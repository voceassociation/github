Le Louvre dépense 80 millions pour sa sûreté. Une API peut encore ouvrir une autre porte

Octobre 2026.

Après le vol de huit joyaux de la Couronne en 2025, le Louvre accélère sa transformation. Son schéma directeur de sûreté représente 80 millions d'euros. Christophe Leribault veut installer une "culture de sécurité".

Mais six mois plus tôt, un autre incident avait montré où une partie du risque s'est déplacée.

Le 2 mars 2026, Vivaticket, fournisseur de billetterie utilisé par des dizaines de sites culturels français, subit une cyberattaque. Des billetteries deviennent indisponibles et un risque de fuite de données personnelles apparaît.

Personne n'a touché une vitrine.

Il a suffi d'atteindre un fournisseur commun.

Une billetterie moderne dialogue avec le paiement, les comptes visiteurs, les CRM et parfois les contrôles d'accès. Le risque dépend donc moins du nom du prestataire que des permissions dont disposent ses identités numériques.

Le Muséum national d'Histoire naturelle l'avait déjà appris en juillet 2025. Une cyberattaque sévère avait mis hors service ses systèmes. Plusieurs services numériques sont restés perturbés pendant des mois.

La question de direction devient alors concrète:

combien de fournisseurs possèdent aujourd'hui une identité capable d'atteindre une fonction critique?

ULTRA®

Le risque le plus difficile à détecter n'est pas toujours une API "piratée".

C'est une API qui fonctionne exactement comme prévu pour une identité qui n'aurait jamais dû disposer d'autant de pouvoir.

OAuth, JWT, certificats ou comptes de service portent des permissions. Si un secret de prestataire est compromis, certaines requêtes peuvent rester techniquement valides: bonne authentification, bon endpoint, bon protocole.

Le problème devient le blast radius: jusqu'où cette identité peut-elle aller?

Une architecture sérieuse limite chaque machine au nécessaire, segmente les API, raccourcit les jetons et fait tourner les secrets.

LI!ght Workforce © VOCE

La billetterie peut être pensée de la même manière.

Un Ticket Agent crée le billet. Un Payment Agent ne dialogue qu'avec le paiement. Un Reservation Agent gère créneaux et jauges. Un Access Agent transforme un billet valide en droit d'entrée temporaire. Un Fraud Agent détecte les anomalies sans pouvoir ouvrir une porte.

Chaque agent possède quelques données, quelques API et quelques droits.

Aucun ne devrait détenir les clés de l'ensemble.

C'est une réduction architecturale du rayon d'explosion.

PANTALONE

La porte la plus dangereuse est parfois celle que personne ne reconnaît comme une porte.
